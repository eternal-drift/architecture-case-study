Architecture Decision Records

Scaling a hybrid cloud / on‑prem content platform

Six real decisions from the AWS control plane of a federated content-integration platform — the cloud side that lets partner apps reach document systems sitting inside customer data centers.

Each record below follows the same shape: the constraint we were actually under, the options we weighed, what we chose, what it cost us, and what changed once it ran in production for a year rather than a sprint.

The constraint that shaped everything: customers will not open inbound firewall ports into their data centers, ever — and the platform still has to be low-latency, reliable at enterprise SLA, and operable by a small team.

I led among a small platform team on the AWS-facing side of this work — API Gateway, Lambda, DynamoDB, SQS/SNS, S3, and the Terraform layer underneath all of it. The decisions below are ones I made directly or drove consensus on with the team.

ADR 001 · Connectivity

Outbound-only WebSocket tunnel between on-prem and cloud

Accepted · in production since GA

Context

The platform's whole value proposition is bridging cloud-hosted consumer apps to on-prem enterprise content systems — document repositories that live inside customer data centers for compliance and data-residency reasons. Those repositories are never going to be directly reachable from the internet.

We needed the cloud control plane to dispatch work to an on-prem agent (the Broker) and get results back near real-time, without asking every enterprise customer's infosec team to open an inbound port. For an enterprise sales motion, "please open a firewall rule" is close to a non-starter — it adds a security review cycle to onboarding and a support burden forever after.

Options considered

Rejected — Inbound cloud→on-prem

Traditional client-server, cloud pushes to an on-prem listener. Requires customers to expose a service to the internet, or stand up VPN/PrivateLink per customer. Kills the "no on-prem infra team required" pitch.

Rejected as primary — Polling

Broker periodically polls for work. Satisfies the no-inbound-ports rule and is simple, but latency is bounded by poll interval — tight polling for low latency means high request volume at scale, most of it for nothing.

Chosen — Outbound persistent WebSocket tunnel

Broker opens and holds a long-lived connection outbound to the Gateway API. Broker initiates it (satisfies the constraint), then the channel is bidirectional and low-latency for its life. Adds connection-lifecycle complexity: reconnect/backoff, keepalive, multi-instance connection tracking.

Decision

We built the outbound-only persistent tunnel using native ASP.NET Core WebSockets rather than a managed WebSocket gateway product. The Broker authenticates via a one-time bootstrap-token exchange, then upgrades to a long-lived connection with its own reconnect/keepalive logic. All dispatch and results flow over this channel; binary payloads explicitly do not (ADR 002). We kept the implementation in-house specifically so connection-routing stayed in our control — this mattered directly for ADR 004.

Tradeoffs

Gave up

  • Managed WebSocket infrastructure — we own connection scaling, routing, and framing ourselves.
  • A standing resource that can silently die (network blip, LB idle timeout) — required real keepalive/monitoring investment.
  • Every protocol change is now a coordinated release across every Broker version in the field.

Got

  • Zero inbound firewall requirement for any customer — removed a security-review blocker from onboarding.
  • Low-latency, cloud-initiated dispatch with no polling overhead.
  • One mechanism every future cloud-to-on-prem feature reuses, not a grab bag of workarounds.

Outcome

This became a documented, enforced platform constraint: any new cloud-to-on-prem feature reuses this tunnel. It has held up at multi-region, multi-hundred-customer scale. The real lesson: reconnect/backoff and connection-health detection needed far more investment than happy-path dispatch — that's where production incidents actually came from.

What I'd reconsider todayI'd look harder at a managed WebSocket gateway up front to offload connection-state tracking — we ended up building a DynamoDB-backed version of that ourselves anyway (ADR 004).

ADR 002 · Data movement

S3 presigned URLs for binary content, not the tunnel

Accepted · in production

Context

The platform moves documents — sometimes large ones, tens to low-hundreds of MB — between consumers, the cloud control plane, and the on-prem Broker. Early on, an iteration sent binary payloads as frames over the same WebSocket tunnel from ADR 001, since the channel already existed and was authenticated.

That caused real problems: one large transfer could saturate a Broker's connection for its duration, during which no other job dispatch or result could get through. At scale, one customer's large-document workflow could visibly degrade responsiveness for every other job on the same connection.

Options considered

Rejected — Chunk & prioritize on the tunnel

Add chunking, backpressure, prioritization to the existing channel. Solvable in principle, but adds real complexity to a channel meant to stay simple, and doesn't fix the core issue: one connection doing two jobs with very different throughput profiles.

Rejected — Dedicated transfer connection

A second WebSocket or raw stream just for binary data. Still constrained by no-inbound for the download direction, and adds another connection type to secure and monitor for no clear gain.

Chosen — Object storage with presigned URLs

Upload: writer puts to S3, receiver gets a presigned GET URL and downloads directly. The tunnel carries only the URL and metadata, never the bytes.

Decision

Binary content must not travel over the WebSocket tunnel — full stop. This became a hard, documented platform rule rather than a per-feature judgment call.

Tradeoffs

Gave up

  • An extra hop and a dependency on object-storage availability for any file-bearing workflow.
  • Presigned URL expiry/scoping had to be right — too long is a security exposure, too short breaks slow-link transfers.
  • Brokers need outbound HTTPS to the storage endpoint specifically, one more egress rule to document.

Got

  • Control-plane latency stays flat regardless of file size or concurrent transfer count.
  • Transfer throughput scales independently of the tunnel — object storage handles concurrency far better than one socket ever could.
  • KMS encryption at rest and standard lifecycle policies for free instead of bespoke handling.

Outcome

Fixed the "one customer's big file degrades everyone" problem outright, and shipped alongside a broader containerized-deployment modernization — easier to land as one coordinated change across every customer's Broker fleet at once.

What I'd reconsider todayPresigned-URL TTL tuning was trial-and-error — too conservative at first, then widened after slow-link failures. I'd bake in adaptive expiry based on payload size and historical transfer time from day one.

ADR 003 · Provisioning

Lambda + SQS for async subscription provisioning

Accepted · in production

Context

When a customer subscribes, control-plane resources need provisioning before the platform is usable — tenant config, initial records, whatever a given app integration requires. This is triggered by an external event, not a waiting HTTP caller. The work is variable in duration and can fail transiently, and a dropped provisioning event means a paying customer who can't use the product, with no signal to anyone that something went wrong.

Options considered

Rejected — Synchronous handler in the Gateway API

Reacts directly to a webhook. Simple, but couples provisioning reliability to Gateway uptime and deploy cadence; a slow step risks tying up request-handling capacity or silently dropping the event on timeout.

Rejected — Always-on worker service

A long-running consumer subscribed to the event stream. Reasonable, but for low, bursty volume it pays for idle compute most of the time and is one more service to deploy and keep healthy.

Chosen — SQS-triggered Lambda

Pay only for actual invocations. Natural retry/backoff and dead-letter handling from the queue. Scales to zero when idle, scales out automatically under burst.

Decision

Subscription-creation events (CloudEvents, published by the upstream subscription system) land on SQS; a Lambda processes each message, provisions what's needed, and replies to a specified address. Failed messages get SQS's built-in retry-with-backoff and a dead-letter queue instead of being silently dropped. We deliberately modeled the Lambda's bootstrapping like our existing .NET API hosting, so it didn't become an unfamiliar island only one engineer could safely touch.

Tradeoffs

Gave up

  • Local dev/debugging is genuinely worse — a Lambda test-harness instead of just running the service.
  • Cold starts are a real, if minor, latency cost — acceptable here since nothing blocks on it synchronously.
  • Debugging a failed run means correlating across queue message, invocation logs, and reply — more parts to trace.

Got

  • Failures don't get silently lost — retry plus DLQ gave us a durable, inspectable "this didn't go through" state.
  • Near-zero idle cost for bursty, infrequent event volume.
  • Provisioning decoupled from the Gateway API's own release cadence and request capacity entirely.

Outcome

Has run without rework since it shipped. The dead-letter queue has paid for itself operationally: on the handful of occasions a downstream dependency had an outage, events queued safely and drained automatically on recovery — zero data loss, no manual intervention.

What I'd reconsider todayI'd push harder on standardizing observability across Lambda and the rest of the .NET fleet from day one — we had a gap where Lambda invocations were harder to correlate in traces, and closing it was retrofit work.

ADR 004 · State

DynamoDB for connection and event-reply state

Accepted · in production

Context

The Gateway API runs as a horizontally scaled, stateless fleet, and each Broker holds a persistent socket (ADR 001) to exactly one pod at a time. Whichever pod handles an incoming request has to know which pod is actually holding that Broker's socket — sockets aren't shareable across processes. A related problem later showed up with the events platform (ADR 005): request/reply state needs tracking across a fleet where a publisher's poll could land on any pod.

Both problems are the same shape: small, high-churn, per-connection or per-request state every pod needs to read and update with low, predictable latency.

Options considered

Rejected — In-memory + gossip

Building a correct gossip protocol for connection ownership is a distributed-systems problem we didn't need to take on, and it doesn't survive pod restarts cleanly.

Rejected — Relational store (Aurora Postgres)

Would work, but this is high write-churn, key-value-shaped state with no relational integrity needs. Using it here adds write load to infrastructure tuned for actual relational data, for no relational benefit.

Rejected — Redis/Valkey cache

Fast and key-value shaped, and already used for session state elsewhere. Not chosen because we wanted durability, not just fast-access ephemerality — a cache eviction losing "who owns this connection" mid-operation was a worse failure mode than the latency cost of durable storage.

Chosen — DynamoDB

Key-value shaped, scales automatically with connection/request volume, durable, and pairs naturally with the Lambda-based provisioning path already using the AWS-native toolchain.

Decision

DynamoDB tracks both connection-ownership metadata (which pod holds which Broker's socket) and events-platform request/reply lifecycle state (metadata, sequence-numbered replies, terminal/expired status).

Tradeoffs

Gave up

  • No relational queries or joins — access has to be shaped around keys designed up front, or fall back to a scan.
  • Another data-store type in the operational surface alongside Aurora and Redis/Valkey.
  • Hot-partition risk needed real design-time thought, not something fixable later without migration.

Got

  • Effectively unbounded horizontal scale for connection/request volume, with no capacity management.
  • Durable state that survives pod restarts cleanly — no special-cased drain logic on rolling deploys.
  • Low, predictable per-item latency exactly where it matters: the hot path of every dispatch and poll.

Outcome

Scaled cleanly through multi-region expansion — separate regional tables rather than a single global table, a deliberate simplicity call over cross-region replication complexity for state that's inherently regional anyway. The main real pain: lost ad-hoc queryability during incident debugging, partially mitigated with targeted secondary indexes added after we learned what questions we actually needed to ask.

What I'd reconsider todayI'd invest more upfront in the access-pattern exercise — writing out every query we'll ever need against a table before choosing keys/indexes — rather than adding indexes reactively after hitting a debugging wall.

ADR 005 · Eventing

Kafka + SQS + DynamoDB for the partner events platform

Accepted · in production

Context

Partners needed to publish events and either fire-and-forget them to interested subscribers, or publish a request and asynchronously poll for replies. Requirements: fan-out to multiple subscribers, a durable pollable request/reply lifecycle spanning minutes, delivery reliable enough for an enterprise SLA, and a publish call that returns fast rather than blocking on downstream delivery.

Options considered

Rejected — Single queue for everything

Point-to-point delivery works fine, but fan-out to multiple subscribers needs one queue wired per subscriber by hand, and gives no durable, replayable log — which we already anticipated needing.

Rejected — Managed pub/sub alone, no durable log

Simpler to operate, but no replay or retained history once delivered or expired. Given known request/reply and eventual-replay needs, too thin on its own.

Chosen — Kafka backbone + per-subscriber SQS + DynamoDB lifecycle state

Kafka gives a durable, replayable, ordered log many subscribers can consume independently. SQS in front of each subscriber gives reliable, individually-retryable delivery. DynamoDB tracks per-request lifecycle state.

Decision

Publisher → plugin validates against schema, persists to a local outbox → 202 Accepted returned immediately → background worker dispatches to the Gateway, which publishes onto Kafka → subscribers consume via their own SQS queue fed from Kafka. For request/reply, response metadata is written to DynamoDB, sequence-numbered, so a publisher can poll in order and explicitly close the lifecycle when done.

Tradeoffs

Gave up

  • The most operationally complex piece in the platform — three systems in one feature's critical path, each with its own failure modes.
  • End-to-end tracing across plugin → outbox → worker → Kafka → subscriber SQS is genuinely hard versus a synchronous call chain.
  • Running Kafka, even managed, is a heavier ongoing commitment than a queue-only alternative — partitions, consumer groups, retention.

Got

  • True fan-out with zero publisher-side complexity — a new subscriber needs no change to the publish path at all.
  • A durable, replayable event history, which later made message replay for failed deliveries nearly free to add.
  • Clean separation of concerns: Kafka is the log, SQS is per-subscriber delivery, DynamoDB is fast lookup state — each doing the one job it's good at.

Outcome

Shipped as the platform's real-time partner-notification capability, one of the larger deliveries of the period. Within a quarter of GA we added access controls, audit logging, pagination, and message replay on top — straightforward additions specifically because the log-based foundation already supported them.

What I'd reconsider todayGiven the operational cost, I'd want to more explicitly validate whether a simpler managed pub/sub-plus-replay offering could meet the requirement before committing to Kafka — we leaned partly on existing team Kafka experience elsewhere in the org, a legitimate factor but one I'd weigh more deliberately next time.

ADR 006 · Infrastructure

Terraform over Crossplane for infrastructure-as-code

Accepted · migration complete

Context

Infrastructure spans networking, IAM, Aurora Postgres, Redis/Valkey, API Gateway, Lambda, SQS, DynamoDB, S3, WAF, KMS, and multi-region deployment — reproducible, reviewable, and safely deployable by a small team without becoming one person's full-time job. We'd started with Crossplane (Kubernetes-native infra management). This wasn't green-field — it was a keep-or-cut-over call made with a year of real operational data behind it.

Options considered

Rejected — Keep Crossplane

Fit teams already deep in Kubernetes tooling, but AWS provider coverage lagged what we needed, debugging a stuck reconciliation loop was often harder than reading a plan diff, and team expertise skewed heavily toward Terraform anyway.

Rejected — Stay hybrid

Split by team or resource type. Rejected because two IaC systems means two mental models and ambiguity about which one owns a given resource — exactly what causes an outage from a change nobody thought would conflict.

Chosen — Terraform, orchestrated via a managed runs platform

Mature, fast-moving AWS provider. terraform plan gives a reviewable diff before anything applies. Much larger hiring pool and existing team familiarity — directly relevant to a small team's bus factor.

Decision

Full migration to Terraform, with a defined hard deployment-order chain — IAM/account foundation → global/DNS → networking → shared infra (load balancers, KMS) → datastores/API Gateway/integrations, several parallelizable once earlier layers exist — orchestrated through a managed runs platform for approval and state, split across dedicated repos by ownership. We made it an explicit, dated cutover rather than an indefinite parallel-run, having learned that undefined transitions just accumulate undocumented exceptions.

Tradeoffs

Gave up

  • Real migration cost — every Crossplane-managed resource had to be imported into Terraform state carefully; get it wrong and you lose track of a resource or trigger an unwanted recreate.
  • Kubernetes-native resource management, which some teams had built real tooling around.
  • Plan/apply is less continuously self-healing than a reconciling controller — drift can accumulate silently between runs; we added drift-detection tooling to compensate.

Got

  • Faster access to new AWS resource types and features as they ship, instead of waiting on provider coverage.
  • A genuinely better review experience — a plan diff any engineer, not just an infra specialist, can sanity-check.
  • One IaC system, one mental model, one review surface — no more "which system actually owns this" ambiguity.

Outcome

Completed on schedule, paired with self-healing provisioning retry and strengthened secret rotation while already touching the infra layer end to end. Since cutover, incidents from unreviewable or poorly-understood infra changes dropped noticeably — the plan-diff review step catches things a reconciliation loop's eventual convergence previously masked until something broke.

What I'd reconsider todayThe state-import phase was the highest-risk part and ran longer than scoped, mostly from undocumented manual tweaks accumulated outside Crossplane's control. I'd budget significantly more time for an infrastructure audit before any future large-scale IaC migration.
